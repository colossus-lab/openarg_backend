Rules:

- Always use double-quoted identifiers for column names that contain spaces, accents, or special characters.
- CRITICAL: In `cache_*` tables most columns are stored as TEXT (even years, numbers, dates). ALWAYS compare those with text literals: WHERE anio = '1980', NOT WHERE anio = 1980. Use CAST(col AS NUMERIC) only for aggregations or arithmetic, never for simple equality/filtering. **The annotated type in the `Columns:` line always wins over this default** — `mart.*` views expose real `integer`/`numeric` columns. Never JOIN a text column to an integer one without an explicit cast (`a.anio = CAST(b.ejercicio_presupuestario AS INTEGER)`); Postgres rejects `integer = text`.
- NUMERIC CASTS — NEVER DISCARD ROWS TO MAKE A CAST WORK (CRITICAL). Argentine data mixes decimal formats in the SAME column: plain integers (`32291165`), comma decimals (`9403175,5`), full Argentine notation (`1.234.567,89`) AND dot decimals (`1086738.69`). A filter like `col ~ '^\-?\d+\.?\d*$'` does NOT protect the query — it silently DROPS every comma-decimal row from the SUM and reports a total that is missing part of the universe. That is a wrong answer presented as a fact, which is worse than no answer. **NORMALIZE, DON'T FILTER.**
  **Do NOT use a blanket `replace(replace(col, '.', ''), ',', '.')`.** It assumes the dot is always a thousands separator, so wherever the dot is the DECIMAL separator it multiplies that row by 100. Measured on real data: that is 75% of the rows in `mart.caba_departamentos_en_venta.precio_m2_dolares` and 33% in `mart.caba_pauta_publicitaria.importe`. Branch on the SHAPE of the whole value, never on which symbol happens to be present:
  `CASE`
  `  WHEN col ~ '^\s*-?[0-9]{1,3}(\.[0-9]{3})+,[0-9]+\s*$' THEN replace(replace(btrim(col),'.',''),',','.')`
  `  WHEN col ~ '^\s*-?[0-9]+,[0-9]+\s*$'                  THEN replace(btrim(col),',','.')`
  `  WHEN col ~ '^\s*-?[0-9]{1,3}(\.[0-9]{3})+\s*$'        THEN replace(btrim(col),'.','')`
  `  WHEN col ~ '^\s*-?[0-9]+(\.[0-9]+)?\s*$'              THEN btrim(col)`
  `END::numeric`
  In order those branches read: `1.234,56` (AR, dot = thousands) · `1234,56` (comma decimal) · `1.234` (dot = thousands) · `1234.56` or `1234` (dot = decimal, or plain integer). A value matching none of them falls through to NULL, so the row still counts in `COUNT(*)` but contributes nothing to the `SUM`. **Null the value, never drop the row** — that is the whole point.
  If the column also carries currency symbols or stray spaces (`$ 99.900,00`), wrap it once with `btrim(regexp_replace(col, '[^0-9,.-]', '', 'g'))` and branch on that instead of on `col`.
  Never use `to_number(col, '999G999G999D99')`. In PostgreSQL `G` and `D` resolve from the server's `lc_numeric`, NOT from the mask, so under a `C`/`en_US` locale they mean the English convention — the exact opposite of Argentine notation, silently.
  **CHECK THE TYPE FIRST — this applies ONLY to TEXT columns.** Every `Columns:` line above annotates the real PostgreSQL type in parentheses, e.g. `Columns: anio (integer), credito_vigente (numeric), jurisdiccion (text)`. A column with no annotation is TEXT. If the type is `numeric`/`integer`/`bigint`/`double precision`/`real`, the value is ALREADY a number: use it directly, `SUM(col)`, guarded only by `WHERE col IS NOT NULL`.
  Two distinct failures if you ignore the type:

  2. Worse, forcing it through with `col::text` CORRUPTS the value: `replace(1234.56::text, '.', '')` yields `123456`, silently multiplying the amount by 100. NEVER cast a numeric column to text to normalize it.
